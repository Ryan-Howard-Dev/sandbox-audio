| R-004 | **JS `subscribeEnded` vs native gapless auto-advance race** — double-advance or stale index when suppress window fails | Playback & Queue, Audio | Medium | High | `architecture-violations.md`; `playback-queue-invariants.md` suppress window; `audio-analysis.md` JS FSM vs native desync risk | **Partly mitigated.** `shouldAdoptNativeExoTransition` now rejects native transitions JS itself initiated: `nativeExoPlayUrl` records the track JS navigated to, and echoes inside a 3s window are ignored. Claimed at that one choke point rather than at the 35 `setQueueIndex` call sites. Comparing against the active envelope was never sufficient — the echo can arrive before `audioEnvelopeRef` updates, so it compares against the *previous* track and passes; that ordering is covered by unit tests. **Update 2026-07-27: the mediaId work is landed and verified.** Native now stamps `env:<envelopeId>` on every `MediaItem` and emits `mediaId` on the transition, and reconciliation uses `findQueueIndexForExoTransition` (mediaId first, URL fallback). This was forced rather than optional: URL matching cannot match a cached track, because the queue holds an `https://` URL while the transition reports `content://…stream-cache-…`, so on a cached book JS adopted *nothing* — native advanced two chapters while `envelopeId` stayed frozen on the first. Reliable matching did amplify the re-drive as predicted, which is what exposed the real R-018 cause. **Still cannot be verified in CI** — `play-direct-queue` drives native directly, leaving the transition handler inert with an empty play queue — so it needs the `queue-skip-probe` device check |
| R-018 | **One skip advances 5–7 tracks** — user-initiated skip overshoots the intended track and settles several entries later | Playback & Queue | High | High | Reproduced on device (OnePlus CPH2581) via `sandboxmusic://e2e/queue-skip-probe?skips=1` | **Fixed and verified on device 2026-07-27.** Root cause was identified by logging the gate's inputs at the moment it decides: every spurious transition carried `reason=3` (`MEDIA_ITEM_TRANSITION_REASON_PLAYLIST_CHANGED`). A skip re-primes the native queue, and rebuilding it emits transitions pointing at items *ahead* of the target — one was measured arriving 2133ms after the navigation, so any slower decode or cache miss pushes it past the 3s ownership window and it is adopted, jumping the index one to two tracks. The gate now rejects `PLAYLIST_CHANGED` and `SEEK` transitions outright and treats only `AUTO` as native's call to make; the timing window remains as a backstop for `AUTO` echoes. A queue rebuild is never evidence a listener moved, whenever it lands. Device evidence: **1/5 runs passed before the fix, 4/4 after** (`queue-skip-probe?skips=2` on a 16-track locker album). Note the probe is a **music-only** assertion — `usesIntervalSeekTransport` routes every audiobook and podcast skip to an interval seek, so the probe correctly reports `refused ... outcome=seek` there. Harness notes for re-running: raise the log buffer (`adb logcat -G 32M`) or results age out mid-run, and fire a different `e2e` deep link immediately before the probe, since delivery of a repeated URL is unreliable. Superseded detail follows. **Earlier candidate fix, which was not sufficient:** An external trace ranked the cause as a post-skip prefetch storm whose transitions were adopted: a skip calls `playUrl` with `resetQueue`, the prefetch effect then enqueues `PREFETCH_AHEAD = 5` tracks, and each enqueue produced a transition whose envelope was *not* the navigation target — so `shouldAdoptNativeExoTransition`, which only rejected the navigation's own envelope, adopted every one and each re-drove `setQueueIndex`. That matches the magnitude exactly: overshoot of 5–7 against a native queue of ~6. The gate now covers every transition inside the ownership window, not just the matching one; in that window JS has reset the native queue and is re-priming it, so every transition is an artifact of the re-prime, and a real gapless advance cannot occur three seconds into a minutes-long track. Covered by unit tests including the five-ahead prefetch case. That narrowing helped but left the race intact, because it only ever raced a clock. Original finding: **pre-existing, not introduced by the R-004 echo gate.** Three consecutive single skips on a 49-chapter LibriVox book went 9→16, 16→22, 23→28 — each landing directly on the wrong index with no intermediate values, so it is not a visible "jump then settle". Logcat shows the skip itself resolving *correctly*: `playUrl` is called for the intended envelope (`…601981`, index 23), and native reports a single `mediaItemTransition` at `index:0 queueLength:1`. The index then climbs five further entries while a burst of `enqueueNext` prefetch and `stream-cache-…` re-enqueues runs. Native queue length at the time was 6, which is close to the observed overshoot and may or may not be coincidence. Root cause not yet identified — do **not** switch the transition handler to mediaId matching until it is, since more reliable matching would amplify whatever is re-driving the index. Index is stable at rest (30s observed, no drift); the overshoot only occurs on skip. Whether music-only queues are affected is **untested** |
